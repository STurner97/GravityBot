## Version numbering scheme

A **version** is what people install. A **build** is a unit of development work. One version
can contain several builds. A build that publishes nothing has no version of its own: its work
goes out in the next version that is published.

### Format

`MAJOR.MINOR.PATCH`, with an optional `-STAGE` suffix: for example `0.1.0-alpha` or `1.0.0`.

- **MAJOR** goes up only for a **full** release. Every full release is a new major version,
  `X.0.0`, with no suffix. Before the first full release MAJOR is `0`, so `1.0.0` is the first.
  It is a deliberate decision, not a side effect of a build.
- **MINOR** goes up when a release adds a body of new scope.
- **PATCH** goes up for fixes only, with no new behaviour.

### Stages

**STAGE** is `alpha` or `beta`. A version with no suffix is **full**.

- **alpha**: for developer testing. In progress; more builds are needed. Not public.
- **beta**: for public or third-party testing. Mostly feature complete; one or two builds may
  remain.
- **full**: the public, final release of that major version. Feature complete.

Work after a full release, towards the next one, carries a suffix again: after `1.0.0`, for
example, `1.1.0-alpha`, then `1.2.0-beta`, then `2.0.0`.

The stage is judged against the project's roadmap or agreed scope, not against a count of builds.
The developer chooses it.

### Where the version lives

GravityBot's version string is the `version` field in `package.json`. Nothing else shows it.
The bot was already in daily use as `1.0.0`, untagged, before pipeline was adopted, so the
developer treats `1.0.0` as the first full release and continues from there. Publishing a
version means deploying the accepted commit to Heroku and tagging it.

Each published version is tagged `v<VERSION>` when its publish phase is signed off. Build tags
(`build/<NN>-<slug>`) are separate. The state file of each build records `version:` and `stage:`,
or `version: none` for a build that publishes nothing, so the table above can match versions to
builds.

### Choosing the next number

Design proposes the version from the build's scope; publish confirms it, or revises it with a
reason if the scope moved.

- A release that adds a body of scope: bump MINOR.
- A release that only fixes defects: bump PATCH.
- Moving from alpha to beta, or from beta to full, changes the stage suffix; the number changes
  only as the rules above say.
- Before `1.0.0`, MINOR releases may change behaviour. Each release note says what changed.
- A number once published is never reused. A withdrawn version is replaced by the next number.
